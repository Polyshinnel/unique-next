# Шаг 14. Проверить Horizon, Filament, API и фронт вручную

## Цель

Пройти пользовательский сценарий целиком: загрузка изображения в Filament, немедленное сохранение исходника, фоновая конвертация, обновление БД, API-ответ и отображение на фронте.

## Зависимости

- Завершены шаги 01-13.
- Контейнер `app` поддерживает WebP.
- Worker/Horizon запущен.

## Задачи

1. Убедиться, что queue worker или Horizon запущен.
2. Зайти в Filament.
3. Создать баннер с `.jpg`.
4. Сразу после сохранения проверить:
   - запись создана;
   - в `banners.image` лежит исходный путь `.jpg`;
   - исходный файл доступен в `storage/app/public/banners`.
5. Дождаться обработки очереди.
6. Проверить:
   - рядом появился `.webp`;
   - в `banners.image` путь заменился на `.webp`;
   - исходный `.jpg` удален, если включен `IMAGE_DELETE_ORIGINAL_AFTER_CONVERSION=true`.
7. Повторить сценарий для `.png`.
8. Загрузить `.webp` и проверить:
   - job не dispatch'ится;
   - путь сразу остается `.webp`.
9. Проверить `/api/banners`:
   - поле `image` возвращает актуальный путь из БД;
   - API не выполняет свою конвертацию.
10. Проверить главную страницу фронта:
   - фон баннера загружается;
   - нет битых ссылок на удаленный исходник.

## Дополнительные проверки гонок

1. Загрузить `.jpg`.
2. До обработки очереди заменить изображение на другой файл.
3. Убедиться, что старая job не перетерла новый путь.
4. Проверить, что в логах нет fatal ошибок.

## Команды и места проверки

Проверка WebP в GD:

```bash
docker-compose exec app php -r "var_export(gd_info()['WebP Support'] ?? null);"
```

Проверка очереди зависит от текущей команды запуска Horizon/worker в проекте. Если используется Horizon:

```bash
docker-compose exec app php artisan horizon:status
```

## Готово, когда

- JPEG и PNG баннеры конвертируются в WebP в фоне.
- WebP баннеры не ставятся на конвертацию.
- API и фронт используют актуальный путь.
- Быстрая замена изображения не приводит к перезаписи новым старым путем.
